# Backup & Restore

Vectora's persistent state lives in two places:

1. **PostgreSQL** — all structured data (users, projects, conversations, documents metadata, settings).
2. **Storage backend** — actual file contents (PDFs, uploads, exports).

LanceDB (vector index) is derived from indexed documents and is **rebuilt automatically** during re-import — it doesn't need separate backup.

## Database backup

### Manual backup

```bash
# Inside Docker Compose
docker compose exec postgres pg_dump -U vectora vectora > backup-$(date +%Y%m%d-%H%M).sql
gzip backup-*.sql
```

### Automated daily backup with cron

```bash
# /etc/cron.d/vectora-backup
0 3 * * * ubuntu cd /home/ubuntu/vectora && \
  docker compose exec -T postgres pg_dump -U vectora vectora | \
  gzip > /backups/db-$(date +\%Y\%m\%d).sql.gz && \
  find /backups -name "db-*.sql.gz" -mtime +30 -delete
```

### Offsite backup with rclone

```bash
# Install rclone and configure S3 remote
rclone copy /backups/ s3:my-backup-bucket/vectora/
```

## Storage backup

If using local storage:

```bash
# Sync uploads directory to S3
aws s3 sync /home/ubuntu/vectora/uploads/ s3://my-backup-bucket/uploads/
```

If using S3 already — enable versioning on the bucket for built-in backup.

## Restore

### Restore database

```bash
# Stop Vectora to prevent writes during restore
docker compose stop vectora

# Drop and recreate the database
docker compose exec postgres psql -U vectora -c "DROP DATABASE IF EXISTS vectora;"
docker compose exec postgres psql -U vectora -c "CREATE DATABASE vectora;"

# Restore
gunzip -c backup-20250315.sql.gz | \
  docker compose exec -T postgres psql -U vectora vectora

# Restart
docker compose start vectora
```

### Restore storage (local)

```bash
# Restore from S3 to local
aws s3 sync s3://my-backup-bucket/uploads/ /home/ubuntu/vectora/uploads/
```

## Point-in-time recovery

For production environments, enable PostgreSQL WAL archiving for PITR:

```sql
-- postgresql.conf
wal_level = replica
archive_mode = on
archive_command = 'cp %p /wal-archive/%f'
```

Or use a managed database with built-in PITR (RDS, Cloud SQL, Supabase).

## Disaster recovery runbook

1. Provision a new server with the same OS and Docker version.
2. Clone your Vectora config (`.env`, `docker-compose.yml`).
3. Pull the Docker image: `docker compose pull`.
4. Restore the database from the latest backup.
5. Restore storage files from the backup bucket.
6. Start the stack: `docker compose up -d`.
7. Verify: `docker compose logs -f vectora` until you see `✓ Server listening`.
8. Test: open the web UI, verify login and a RAG query.

## RTO / RPO targets

| Scenario | Target |
|---|---|
| RPO (data loss window) | ≤ 24h (daily backup), ≤ 1h (WAL archiving) |
| RTO (recovery time) | ≤ 30 minutes with documented runbook |
